需求方案 02｜DG-01 商务移交与提前开工

P1 在同一项目空间完成交付可接收性检查；提前开工只允许限定范围先行，不自动通过 DG-01。DG-01 通过形成移交包，P2 准备并通过 DG-02 后才正式进入交付。

零、进入 DG-01 的业务前提
项目空间·售前
规定动作与 SG-02 已形成结果
→
中标/成交/合同路径
按采购方式回显“中标”或“成交”
或
提前开工申请获批
作为批准范围内的开工依据

未中标、客户取消或主动终止时，项目空间以“售前｜已关闭｜对应业务结果”只读保留，不进入 DG-01。提前开工获批时业务结果可以继续为“待定”。

一、移交资料包｜由商务发起，系统先做完整性检查
项目基础
客户、现场、设备、干系人、关键时间
商务依据
合同/中标/委托依据、金额、付款节点
范围与技术
需求、方案、供货范围、边界、接口与差异
验收与计划
验收标准、生产窗口、目标工期、关键节点
投入与风险
初始约束、资源需求、遗留问题、风险与承诺
二、正常准入与限定先行｜都不能跳过正式阶段门
路径 A｜正常交付准入
商务提交
完整移交包
→
联合评审
拟任项目经理/交付代表＋技术＋相关部门
→
DG-01 通过
形成可接收移交包
  • 范围、验收、时间和商务依据达到准入要求
  • 初始资源和交付约束已识别，详细团队承诺在 DG-02 完成
  • 资料不足时退回，并生成缺项清单
路径 B｜提前开工例外
例外申请
说明缺失与必要性
→
风险会签
技术、预算、资源评估
→
公司级批准
限范围、限预算、限期限
  • 批准后可在限定范围内先行，但 DG-01 仍保持待补齐/待通过
  • 必须填写启动依据、临时范围和预算上限
  • 逐项登记缺失资料、责任人及补齐期限
  • 以最小承诺台账记录金额/工时、责任人、依据和实际发生
  • 明确风险承担人、停止条件和到期日期
三、P1 输出与 P2 起点不能混在一起
P1｜DG-01 通过后形成
移交结论、当前有效移交包、缺项/例外清单、初始范围与风险、合同/中标/委托依据，以及进入 P2 的待办。
P2｜先准备、再通过 DG-02
P2 开始即开放团队、执行阶段、项目清单、专业工作包、主计划和预算草案；DG-02 评审通过后，同一批对象转为正式基线、主阶段变为“交付”，并形成 P3 执行准入条件。
四、提前开工的到期控制
例外获批
只允许批准范围内工作
逐笔记录承诺与实际
→
补齐与转正
签约、资料补齐后完成 DG-01，并在 P2 建立 DG-02 基线
／
到期/超范围/超预算
冻结新增承诺并升级公司裁决
审计原则：所有退回、补充、例外批准、承诺占用、范围变化和转正过程保留版本与时间记录，不能覆盖原始交底内容；提前开工不是 DG-01 或 DG-02 的隐式“已通过”。
