需求方案 04｜需求池、问题、风险、变更与安全闭环

需求池与风险管理都是项目空间独立入口并贯穿售前、交付和维护；五类事项保持语义独立，共用责任、处理、验证和关闭的证据链。

分批边界：P1 实现多来源需求的记录、澄清、影响评估、人工派生/关联和验证关闭；P3 再实现完整的问题、风险、正式变更、安全事项、升级与穿透分析。
一、五类事项分别管理，但使用同一闭环机制
项目需求
商务、售前、交付、客户和项目组提出
原需求始终保留
问题 / 缺陷
已经发生并影响执行
如 Bug、接口异常、到货不符、现场阻塞
风险
尚未发生但可能影响项目
等级、规则、责任、验证和应对由人员维护
变更
范围、技术、工期、预算或验收基线发生调整
必须先评估影响再批准
安全事项
隐患、违章、事故、培训与保险
高等级事项可直接触发停工和升级
二、需求池｜人工选择去向，原需求始终保留
记录与澄清
来源、提出人、期望、资料
→
影响评估
范围、技术、工期、成本、合同、验收、安全
→
人工派生或关联
问题 / 工作包 / 任务 / 变更；也可直接实施、保留或拒绝
→
验证关闭
提出方/内部负责人或指定验证人确认

系统不自动决定需求去向。处理人只能提交完成证据；原需求与工作包、任务、问题、变更、成果和验证记录双向追溯。

三、统一闭环：处理人不能自行宣告完成
发现登记
来源、现场、图片、关联任务
→
分级分派
类别、严重度、责任人、期限
→
分析处置
原因、方案、协同任务、证据
→
提交验证
处理人申请完成
→
验证关闭
提出方或指定验收人确认
逾期自动升级 重大问题进入周报 关闭必须有验证证据 重复问题进入产品改进库
风险转问题：系统不自动评分，也不自动转化。风险实际发生时，由人员手动派生或关联问题，并保留原风险与问题的追溯关系。
四、变更控制：先评估，再改变项目基线
变更申请
来源、内容、原因、紧迫性
→
联合影响评估
范围、技术、工期、成本、合同、验收、安全
→
分级审批
一般变更 / 重大变更
→
更新并通知
计划、预算、任务、文件与验收基线生成新版本
紧急变更：允许先执行止损或安全处置，但必须在限定时间内补录原因、影响和审批，不能长期以“现场紧急”为由跳过流程。
五、安全管理不是只上传培训表
准入检查
保险、资质、培训、人员名单
作业方案
吊装、焊接、通电、调试风险
日常检查
现场记录、隐患、整改
事件响应
停工、通报、调查、复工审批
统计复盘
类型、频次、责任、预防措施
六、一项目一清单，但全公司可以穿透分析
项目问题清单
项目成员只看与本项目有关的事项
→
产品 / 机型
专业 / 工作包
需求 / 缺陷 / 供应商
重复发生 / 根因

聊天可以通知和讨论，但只有系统中的事项状态、处理记录与验证结果才构成正式闭环。
