# ADR-001：P1 应用运行形态与模块部署策略

> 状态：已接受  
> 日期：2026-08-26  
> 决策人：项目负责人  
> 关联需求：PRD V0.4 的 P1/P2 产品基线、权限、审计、文件、任务与阶段门要求  
> 关联验证：核心模块 interface 测试；导入、文件、待办与阶段门的并发和故障恢复验证；上线前容量压测

## 背景与问题

P1/P2 涉及强事务关系、跨对象版本、权限和审计。预计总用户数为 60—100 人，团队更熟悉 Java，公司没有必须复用的既有技术栈。系统需要在保持后续 P2—P4 演进能力的同时，避免首期引入多服务部署、跨服务事务和运维协调成本。

## 决策驱动因素

- DG-01、DG-02、项目空间、权限、文件和审计需要一致的正式事实；
- 首期用户规模和交付节奏不支持为每个业务模块建立独立运行单元；
- 导入、通知、重试和文件处理不能长期阻塞用户请求；
- 模块边界必须可测试，未来可在有证据时拆分。

## 候选方案

### 方案 A：模块化单体加独立后台任务进程

一个代码仓库和一个业务应用进程承载逻辑模块；模块通过稳定 interface 协作。后台任务使用同一代码库的独立 Worker 进程执行。优点是事务边界清晰、部署与调试成本低，并保留任务隔离和后续拆分空间。

### 方案 B：首期微服务

按客户、商机、文件、权限、消息等拆成独立服务。优点是理论上的独立部署与扩缩；缺点是首期引入远程调用、分布式事务、版本协调、可观测性和运行成本，与当前规模不匹配。

### 方案 C：单一应用进程执行全部工作

部署最简单，但导入、重试和后续文件处理会与用户请求竞争资源，故不作为 P1 基线。

## 验证证据

- 已确认公司私有部署、员工 VPN 访问、自建账号、60—100 总用户规模和 Java 团队能力；
- PRD 要求 DG-02、权限、审计和文件事实可追溯且不能产生多套正式状态；
- 尚未获得证明必须独立扩缩或由独立团队自治的容量和组织证据。

## 决策

P1 采用模块化单体加独立后台任务进程：

- 业务应用按客户商机、项目空间、售前、阶段门、交付立项、资料、权限、工作台、配置、审计和任务等逻辑模块组织；
- 跨模块调用只使用模块公开 interface，不允许跨模块直接修改数据；
- 业务应用与 Worker 可先同环境、独立进程部署；是否使用独立主机由容量和故障隔离证据决定；
- 不以微服务、Kubernetes、独立缓存、消息队列或搜索集群作为 P1 前置条件；
- 任何将模块拆为网络服务的提议，都必须提供独立扩缩、强隔离、独立发布或团队自治证据，并新建 ADR。

## 后果

### 正向后果

- P1 可以以清晰的事务边界和较低运维成本交付；
- 模块 interface 是单元、集成和后续拆分时的稳定测试面；
- Worker 将长任务与交互请求隔离。

### 负向后果与控制

- 单体不等于模块可随意互相访问：代码结构、测试和评审必须保护模块边界；
- 单个应用进程可能成为资源瓶颈：上线前以真实容量和关键旅程压测验证；
- 未来拆分需先稳定数据所有权和事件契约，不能直接按目录或表拆服务。

## 迁移与回退

Worker 可先与应用部署在同一环境，后续无业务协议变化地迁往独立节点。任何微服务拆分应先在模块边界建立受控 port 和 Adapter，并用新 ADR 记录数据迁移、回退和一致性策略。

## 复审触发条件

- 真实压测或运行数据表明应用与 Worker 无法满足目标；
- 某模块出现独立扩缩、强网络隔离或独立发布的可验证需求；
- 团队变为多个可独立维护且能承担运行责任的小组；
- RPO/RTO 或可用性要求明确要求不同故障域。
