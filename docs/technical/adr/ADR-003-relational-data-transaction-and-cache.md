# ADR-003：P1 结构化数据、事务、缓存与高可用边界

> 状态：已接受  
> 日期：2026-08-26  
> 决策人：项目负责人  
> 关联需求：PRD V0.4 的客户/商机、项目空间、阶段门、版本、权限、审计、数据任务和分析要求  
> 关联验证：迁移回滚、并发更新、DG-02 一致性、任务领取、权限撤销与恢复演练

## 背景与问题

产品存在大量强关系对象、跨对象版本、审计历史、权限判断和阶段门不变量。当前预计总用户数为 60—100 人，尚未证明需要分布式缓存或数据库多活。选择应先确保数据一致性和可维护性，而不是预先追求复杂的扩缩形态。

## 决策驱动因素

- 业务事实、版本、权限、审计和任务之间需要可靠事务；
- DG-02 提交、通过和基线生效不能出现部分完成；
- 数据、审计需长期保留；
- 首期运行和恢复成本应与实际规模相称。

## 候选方案

### 方案 A：PostgreSQL 为主的关系型存储

使用关系约束、事务、索引和迁移管理保存业务事实、账号权限、审计、任务和文件元数据。适合当前对象关系和一致性要求。

### 方案 B：多个专用数据存储和独立缓存

可针对局部读写模式优化，但会增加同步、一致性、备份、权限过滤和运行成本。在当前规模缺乏必要证据。

### 方案 C：非关系型数据库为业务事实主库

对版本关系、阶段门事务和审计追溯不利，首期不采用。

## 验证证据

- PRD 明确要求正式事实唯一、历史不覆盖、权限可解释和阶段门可追溯；
- 预计用户规模低于需要首期分片或多活的合理门槛；
- 团队采用 Java，PostgreSQL 与所选服务框架成熟兼容。

## 决策

- PostgreSQL 是 P1 的结构化事实主库；
- 业务事实、角色权限、审计事件、可靠任务/事件和文件元数据均使用关系模型管理；
- 关键业务操作在数据库事务中完成，并以显式版本、约束、幂等键和并发控制保护不变量；
- P1 不引入独立 Redis 或其他分布式缓存；会话撤销和账户状态使用低运维的服务端机制实现；
- 高可用、只读副本、异地容灾和具体备份策略留待 RPO/RTO、运行平台和恢复演练要求明确后由 ADR-009 定版；
- 精确 PostgreSQL 主版本、扩展、迁移工具和连接池配置在工程初始化时选用受支持版本，并纳入依赖和备份验证。

## 后果

### 正向后果

- 关键流程有清晰、可验证的事务边界；
- 运维对象少，适合当前用户规模；
- 版本、审计、权限和任务可用统一关联号追溯。

### 负向后果与控制

- 数据库是关键依赖：备份、恢复、监控和容量不能被忽略；
- 不使用独立缓存意味着热点性能需以真实数据验证；
- 对 PostgreSQL 的专用特性应保持克制，关键数据导出与迁移必须使用开放格式。

## 迁移与回退

所有数据库变更采用可审查的前向迁移和备份恢复验证。新建缓存、读写分离或专用存储前，必须先证明瓶颈并通过新 ADR 规定数据所有权、同步、回退和恢复方式。

## 复审触发条件

- 压测表明关键旅程无法满足目标；
- RPO/RTO 或高可用要求需要新的数据库拓扑；
- 数据量、查询模式或团队运行能力发生实质变化；
- 必须引入新的主数据存储产品。
