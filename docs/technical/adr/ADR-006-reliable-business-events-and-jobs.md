# ADR-006：P1 业务事件、后台任务与可靠投递

> 状态：已接受  
> 日期：2026-08-26  
> 决策人：项目负责人  
> 关联需求：PRD V0.4 的工作台、待办、消息、审计、Excel 迁移、文件处理和后续飞书提醒要求  
> 关联验证：重复投递、任务重试、Worker 中断、租约恢复、幂等处理和人工处置验证

## 背景与问题

业务完成后需要生成待办、消息、审计、导入结果和未来外部提醒。若业务数据已经提交而后续任务丢失，会造成正式事实与协作状态不一致。首期用户规模有限，尚没有必须引入独立消息队列的吞吐或隔离证据。

## 决策驱动因素

- 业务事实与待发布事件必须可靠关联；
- 导入、通知和重试不能阻塞交互请求；
- 重复请求、超时和 Worker 故障必须可恢复；
- 运行组件数应与当前规模相称。

## 候选方案

### 方案 A：PostgreSQL 事务内事件/任务记录加独立 Worker

业务事务中写入可靠事件或任务记录；独立 Java Worker 用租约领取、执行、重试和记录结果。实现较少、可追溯，并能在未来以 Adapter 对接队列。

### 方案 B：首期引入独立消息队列

可提供更高吞吐和隔离，但增加集群、监控、重复消费、备份和运维成本。当前不作为前置条件。

### 方案 C：同步执行所有副作用

会使页面请求受导入、通知或外部系统影响，也难以恢复，不采用。

## 验证证据

- PRD 已确认站内待办、消息、任务状态、导入结果和审计；
- 飞书不阻塞 P1，外部渠道失败不能回滚正式业务事实；
- 当前总用户规模不构成必须首期建设队列平台的证据。

## 决策

- 业务模块在保存正式事实的同一数据库事务中记录业务事件或后台任务；
- 独立 Java Worker 通过租约或等价机制领取任务，保存心跳、执行尝试、幂等键、结果和人工处置状态；
- 任务状态统一表达为待执行、执行中、部分成功、成功、失败或已取消；重试创建新的尝试，不覆盖失败证据；
- 待办和消息是源业务事实的派生协作项，完成动作必须回到源模块验证；
- 飞书、NAS、财务等外部 Adapter 仅在真实接口条件具备后接入；失败只进入重试或人工处置，不回滚已完成业务；
- P1 不以独立消息队列作为前提。若未来接入队列，仍以业务事件和幂等契约为稳定边界。

## 后果

### 正向后果

- 业务与协作副作用可通过同一关联号追溯；
- Worker 不阻塞用户请求，且具备可恢复的失败状态；
- 首期运行成本低于队列集群方案。

### 负向后果与控制

- 任务表和 Worker 需要索引、监控、租约恢复和容量测试；
- 长任务不能无限占用 Worker：对应任务 SPEC 需定义超时、并发度和分片；多个任务共用的运行约束进入后端共享设计；
- 未来队列迁移仍须验证顺序、重复、备份和灾备。

## 迁移与回退

事件类型、对象标识、幂等键和结果状态是稳定契约。未来队列 Adapter 可以从可靠事件记录读取并投递；切换期间必须防止双重消费和重复有效待办。

## 复审触发条件

- 任务吞吐、延迟或隔离要求经验证超过数据库 Worker 能力；
- 需要跨多个运行域进行可靠投递；
- 外部渠道数量和失败补偿复杂度显著上升。
