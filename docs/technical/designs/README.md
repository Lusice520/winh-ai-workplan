# 跨功能共享设计

本目录只维护会被多个功能共同遵守的技术设计，例如前端组件规范、统一接口约定、数据库迁移规则、权限模型、文件契约和运行规范。

## 与 SPEC、ADR 的边界

| 内容 | 唯一维护位置 |
|---|---|
| 单功能页面、流程、字段、接口、数据、异常、实现和测试设计 | 对应 `docs/requirements/specs/` 下的 SPEC |
| 多个功能共同使用的组件、契约、规则或运行方式 | `docs/technical/designs/` 下的共享设计 |
| 有多个有效方案、会显著影响架构或维护成本的技术取舍 | `docs/technical/adr/` 下的 ADR |

本项目不再为每个功能建立平行的 `DES-XXX` 文档，也不以 DES 清单作为工程搭建门槛。一个设计只有在至少两个功能需要共同遵守，或者它跨越构建、部署、安全、数据和运行边界时，才进入本目录。

## 子目录职责

| 目录 | 中文含义 | 放什么 |
|---|---|---|
| [frontend](./frontend/README.md) | 前端共享设计 | 技术栈、设计令牌、组件使用、路由、状态、表单、表格、错误和测试规范。 |
| [backend](./backend/README.md) | 后端共享设计 | API、错误、数据库迁移、后台任务、可观测性和部署运行规范。 |
| [shared](./shared/README.md) | 跨端共享设计 | 身份权限、文件、状态、审计、事件等前后端共同遵守的契约。 |

## 建立共享设计的条件

建立文件前逐项确认：

1. 已有至少两个功能需要共同遵守，或该设计影响整个工程的安全、数据、构建或运行。
2. 内容是可复用约束，不是某个功能的页面、字段、接口和验收细节。
3. 关联的 SPEC 与 ADR 已明确，且共享设计不会反向改写产品事实。
4. 能通过代码、自动化检查或可重复场景验证，而不只是原则描述。

不满足这些条件时，设计内容留在对应 SPEC。

## 共享设计建议结构

```markdown
# 共享设计标题

> 状态：草稿 / 评审中 / 已基线 / 已替代
> 适用范围：
> 关联 SPEC / ADR：

## 1. 目标、范围与非目标
## 2. 统一契约与不变量
## 3. 推荐实现与复用方式
## 4. 例外、兼容和迁移
## 5. 安全、数据与运行影响
## 6. 验证方式
## 7. 风险与未决项
```
